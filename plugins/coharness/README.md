# CoHarness 寄宿于 dsh

CoHarness 把项目阅读、开发和审阅放入三个空间。dsh 提供客户端外壳、工作区、认证、模型循环和持久化存储。插件使用 TypeScript 处理文件和 Git。插件不依赖 Python HTTP 服务。

## 用户在三个空间协作

| 空间 | 当前功能 |
| --- | --- |
| 项目空间 | 打开目录、模型生成项目概览、架构演示动画、场景阅读、源码依据、目录分层浏览、文件搜索、分段读取 |
| 开发空间 | 保存需求、生成并应用模型修改方案、查看修改自述、编辑文件、保存工作快照、暂存任务、恢复任务 |
| 审阅空间 | 当前修改、提交历史、双栏差异、每项修改自述、AI 修改动机、用户批注、调用候选、上下文抽屉、预期对齐、验证状态、继续开发 |

模型每次生成概览时同时提交 `architectureHtml`。模型决定模块分层、关系箭头、布局、颜色和展开说明。客户端使用结构化的模块、关系和场景绘制架构演示动画。客户端把模型 HTML 收进可展开的详细架构图。客户端不生成项目关系数据。

架构页面使用隔离 iframe。浏览器禁止脚本、外部资源和父页面访问。模型可以使用 HTML details 和 CSS 实现展开交互。用户可以展开整个架构页面。

文件编辑保存工作快照。模型修改方案需要用户确认后才写入文件。用户确认预期后，系统保存对齐记录。上述操作均不会自动创建 Git 提交。提交需要用户单独填写说明并确认。恢复任务使用 `git stash apply --index`，系统保留 stash 备份。

## 项目空间先播放架构演示

项目概览生成后，项目空间先展示一个小型架构演示动画。动画使用概览中的模块、relations 和场景步骤，不读取模型 HTML 的布局。

动画提供“总览”和最多四个使用场景。总览依次说明项目用途、模块分工和依赖数量。场景轨道按照模型给出的阅读步骤移动高亮，并保留每一步的文件依据。

用户暂停、前进、后退或选择场景。动画尊重 `prefers-reduced-motion`，在用户要求减少动效时保持静止。动画不代表运行时调用链，系统没有运行项目。

模型生成的 HTML 保留在“模型生成的详细架构图”折叠区。HTML 继续使用隔离 iframe 和内容安全策略。

## 审阅自述连接开发

审阅空间为每个修改项生成“修改自述”。自述来自实际差异、函数位置、同文件调用候选、当前需求和用户预期。

自述列出改动范围、增减行、涉及函数和任务阶段。自述提供新增行与删除行片段，并给出继续开发的核对点。系统不推断修改动机，不把静态说明写成运行验证。

开发空间的当前任务页列出本次修改的文件和自述摘要。用户从开发空间进入审阅时，系统保留同一文件和同一修改项。用户从审阅空间返回开发时，系统打开同一文件并定位到修改起始行。

两个空间使用同一条工作链显示当前需求、文件、修改项和对齐状态。系统保留各空间的阅读位置和未保存草稿。

## 自己开发自己的闭环

开发空间现在把需求接到模型修改循环。用户按以下顺序推进。

1. 用户保存当前需求。
2. 用户点击“生成修改方案”。
3. 模型使用只读工具列出和读取相关文件。
4. 模型提交 `find` / `replace` 形式的修改方案。
5. 系统在内存中预演方案。系统拒绝歧义替换、重复替换和不存在的目标。
6. 用户查看每处修改的动机、预期和文件依据。
7. 用户点击“应用方案并写入文件”。系统按文件版本检查和写入。系统在某次写入失败时尽力回滚已经写入的文件。
8. 系统保存每处修改的模型动机、证据和最终行号。
9. 用户在审阅空间查看差异、动机和批注。
10. 用户运行测试、类型检查和插件构建。
11. 用户填写提交说明并创建 Git 提交。
12. 用户把批注加入需求，开始下一轮。

模型不会直接写文件。模型不会自动提交。用户始终确认方案应用和提交。

## 模型动机与用户批注

模型每提交一处修改，都同时提交 `reason`、`expected` 和 `sourceIds`。系统把 `sourceIds` 转换为文件、起止行和依据摘要。

方案应用后，系统把每处动机绑定到文件版本和最终行号。审阅空间按路径和行号范围匹配动机。文件在之后变化时，系统标记动机已过期。

用户可以在动机旁边写批注。系统把批注绑定到修改项和文件版本。用户可以点击“加入需求”。系统把批注追加到当前需求。下一次模型修改循环会读取这些批注。

批注保存在操作日志中。系统不会把批注写入源码注释。

## 运行验证与提交

开发空间提供三个验证入口：运行测试、类型检查、构建插件。系统只运行 `plugins/coharness/package.json` 中声明的 `test`、`typecheck` 和 `build`。系统不执行任意命令。

验证结果和对齐状态分开保存。对齐状态不会变成测试通过。验证后文件再次变化时，系统标记本次结果已经过期。

用户填写提交说明后可以创建 Git 提交。系统暂存当前工作区的全部变动文件。系统不会自动提交。提交前不会自动运行验证。

用户点击“构建插件”时，系统在插件目录运行 `pnpm run build`。客户端产物更新后由 dsh 的客户端热更新接收。宿主代码更新需要重启 dsh web。页面会明确显示这一限制。

## 编辑器布局

文件浏览与开发空间使用紧凑文件树和文件标签。CodeMirror 提供语法高亮、行号、折叠、搜索和撤销。开发空间支持 Ctrl/Cmd+S 保存工作快照。页面保留未保存草稿。

审阅空间使用双栏差异。顶部下拉框选择修改项。右侧面板先解释当前修改，再保存预期和对齐状态。用户可以展开或收起右侧面板。调用上下文继续支持展开和返回原修改项。

开发空间的文件工具栏保留“修改自述”和“审阅修改”。工作链条始终显示当前需求、文件、修改项和对齐状态。

## 系统保存真实记录

`coharness_overview` 保存概览版本与最近生成编号。每条引用保留路径、行号、SHA-256 和源码片段。

`coharness_ide` 保存操作日志。每条日志同时携带状态值与序号。系统从日志恢复需求、快照、暂存关联、对齐记录、修改方案、模型动机、用户批注、验证结果和提交记录。

开发启动脚本通过 `COHARNESS_LEGACY_STATE_DIR` 指定旧状态目录。插件首次打开对应工作区时读取旧 SQLite 数据。插件使用 Node 的 SQLite 接口。旧数据库保持原样。插件保留旧审计记录；旧对齐快照不会自动成为新快照的已对齐状态。

## 用户启动插件

项目固定使用 dsh 0.2.1-alpha.1。插件要求 Node 22.19+ 或 Node 24+。

```sh
pnpm install
pnpm run typecheck
pnpm test
pnpm run build
```

用户在现有 dsh 环境安装本地插件：

```sh
dsh plugin --profile web add file:/完整路径/plugins/coharness
dsh web
```

本仓库的 `pnpm run dev` 使用 `.coharness/dsh-dev` 中的隔离 dsh。脚本在 3081 端口启动 Web 客户端。模型使用 dsh 已配置的默认模型与凭据。

宿主代码更新后，用户停止 dsh web 并再次启动。客户端产物可以通过界面“构建插件”更新。宿主进程不会由插件自行重启。

## 当前边界

模型已接入项目概览和开发方案。模型方案必须由用户确认后写入。模型不会自动提交。模型动机是模型生成的说明，不是运行验证。

验证只覆盖插件固定的三个脚本。系统不执行任意命令，不创建测试报告文件。用户对齐不会被标记为测试通过。

客户端插件更新可以通过界面构建。宿主插件代码更新需要重启 dsh web。当前没有从界面重启宿主进程的入口。

调用关系是语法层面的同文件候选。系统不会把动态调用或跨文件引用伪装为已确认调用。模块架构关系由模型根据引用依据生成。

修改自述只解释可见差异和已有记录。系统不推断作者动机。AI 动机来自模型方案，必须和差异范围匹配后才展示。架构演示使用模型结构化概览，动画路径不代表实际执行路径。

文件正文按需分段读取。差异预载保留 1000 文件、单文件 512 KiB、总计 8 MiB 的边界。大型历史差异目前显示范围提示。修改方案只支持文本替换和新建文本文件，不支持重命名、二进制文件和目录操作。

旧 `coharness/` 目录保留为迁移参考。用户审核通过前，系统不会删除旧原型。
